# LLM 灾害管理综述 复现笔记（第 5 篇）

> 复现论文：Harnessing Large Language Models for Disaster Management: A Survey
> （ACL 2025 Findings，arXiv:2501.06932）
> 用到的模型：智谱 GLM-4-Flash（API 调用）
> 时间：2026年10月

## 这是一篇综述，到底怎么复现

系统论文有实验、有数字，照着搭一遍比对指标就行。综述没有这个，
它连自己的实验都没有，全是把别人的工作归类罗列。所以硬要"复现综述"
是复现不出东西的。

我想了半天，干脆换另一条路：把它那套分类框架当成一个可以拎出来的
组件，用代码实现一遍，再让大模型拿着它去干活。具体说，综述最大的贡献
是 Figure 1 那张图——灾害分成缓解/准备/响应/恢复四阶段，每个阶段下面是
各种任务，旁边还标注了适合的模型类型（ELM/DLM/MLLM）。这张图本质上是
一份"灾情文本长什么样、该归到哪、该配什么模型"的规则表。

那我就把这份规则表抽出来写成 `taxonomy.json`，再写个工具：输入一段中文
灾情文本或者情报，让 GLM 严格按这套框架输出一个结构化 JSON，
包含它判定的阶段、子任务、建议的模型类型，以及判定依据。这样综述的
静态框架就变成了一段能拿真数据跑、能算准不准的代码。这也是我理解的
"综述的可提取组件复现"。

## 这项目干了啥

这项目干了啥，直说吧：一个小工具 `extract.py`，
给它一段中文灾情文本，它按 `taxonomy.json` 里的框架吐出来
`{阶段, 子任务, 建议模型类型, 依据}`；再加一个 `eval.py`，
用我自己写的 12 条测试文本跑一遍，统计阶段判定和子任务命中准不准。

`taxonomy.json` 里编码了这些（数字都是从论文笔记里搬的事实）：

- 四个阶段：灾害缓解（论文占比 1.6%）、灾害准备（12.6%）、
  灾害响应（72.4%）、灾害恢复（13.4%）
- 响应阶段的五个子任务：灾害识别、灾害态势评估、灾害信息协调、
  灾害救援、灾害问题咨询
- 态势评估的三小细分：态势分类、严重程度估计、灾情描述生成
- 三种模型类型：ELM（编码器，像 BERT）、DLM（解码器，像 GPT）、
  MLLM（多模态）
- 综述 Appendix B 里整理的五个代表数据集：CrisisLex、CrisisMMD、
  Damage Multimodal Dataset、AIDR、CrisisNLP

响应阶段占了七成多，我的研究方向（态势推理）正好落在这一格里，
所以这个工具的主战场也在这五个子任务的切分上。

## 怎么跑

```
# 装依赖（.venv 已有的话跳过）
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

# .env 里填智谱 API Key（格式：ZHIPUAI_API_KEY=你的key）

# 单条抽取，看模型怎么判
.venv\Scripts\python.exe extract.py
.venv\Scripts\python.exe extract.py "你的灾情文本"

# 跑 12 条评测，统计准确率（结果缓存 results/predictions.json，跑挂可续）
.venv\Scripts\python.exe eval.py
```

## 核心思路

框架是死的，判定是活的，中间全靠提示词把 `taxonomy.json` 翻译成
一段模型能照着做的规则。我在提示词里做了三件事：

一是把 taxonomy 摊平成人话塞进去，四阶段的占比、每个任务的定义、
三种模型类型的适用场景全写清楚；二是定死输出格式，
只准输出一个 JSON 对象、字段名固定四个；三是专门提醒它
"信息协调和态势评估容易混，要说清楚为什么不是相邻的那个"——
这句是因为我在论文笔记里就记了这两个任务边界模糊，想看看它分不分得清。

程序这边再用正则把模型输出里的 ```` ```json ```` 外壳剥掉，
防止它包一层代码块导致解析崩。

## 测试记录

12 条测试文本，温度 0.1：

| 指标 | 结果 |
|---|---|
| 阶段判定准确率 | 12/12 = 1.000 |
| 子任务命中率 | 11/12 = 0.917 |
| 阶段且子任务都对 | 11/12 = 0.917 |
| 建议模型类型与参考值一致 | 7/12 = 0.583 |
| 态势评估三小细分命中 | 2/3 = 0.667 |

阶段四选一全对，不意外。子任务那一条错的是 R2：
文本明明在问"这属于哪一种灾害"，模型却归到了**灾害识别**，
没归到**灾害态势评估（态势分类）**。它给的依据还挺像回事，
说"更侧重对灾害类型的判断，不涉及严重程度或救援"。
问题是"识别"在论文里指的是"这条消息跟灾害有没有关系"那种相关性判断，
"判断是哪种灾害"属于态势分类。模型自己造了一条分界线，
把识别和分类并成一个任务，所以判偏了。

这事不怪模型，怪框架。综述里 Identification 和 Situation Assessment
的界线本来就糊，我在笔记里就写过这个疑问，这次算是亲手撞上了——
提示词里我没法把两者的区别讲得让它无歧义。这是这次复现我觉得最真实
的一处结果，没藏。

模型类型那项只有 0.583，也不是精度低，是模型一味往 ELM 上靠：
连信息协调、救援方案、问题咨询、重建排序这些明显要生成文字的任务，
它都选 ELM，理由是"擅长理解和分类"。唯独在"灾情描述生成"和"写预警信息"
这两条上它老老实实选了 DLM，说明它知道生成配 DLM，
只是对"规划/协调/咨询"这类看不出要生成的要靠规则兜。
我给的参考类型（分类→ELM、生成→DLM）是我按综述思路定的，不是论文硬标准，
这个 0.583 只能算粗糙摸底。

## 踩过的坑

**1. 综述的"复现"得像这样绕一下，不能硬凑实验。**
我一开始想按系统论文的套路搭个"灾害分类器"再报准确率，
写着写着发现跟这篇综述没关系了——它压根没提这个模型。
后来才想通，正确姿势是复现它的**框架**（可提取的组件），
而不是复现它的**结论**（它没有结论）。想清楚这点之后一晚上就写完了。

**2. 框架里的边界含糊，会直接变成代码里的错误。**
上面 R2 就是活例子。论文把 Information Coordination 和 Situation Assessment
并列列出来，但没给"什么算识别、什么算评估"的操作性定义，
到了让模型做硬判定的时候，这个含糊就变成了实打实的判错。

**3. 模型总要包一层 markdown 代码块。**
提示词里明写了"不要代码块"，GLM 大部分时候还是输出
```` ```json ... ``` ````。一开始解析直接崩，后来加了正则剥壳才稳。
llm-crisis-demo 那边也遇到过不听话的，这次是格式层面，靠剥壳解决。

**4. 评测脚本自己的 bug 差点让我给错分。**
第一版跑完，"态势评估细分命中"显示 0/3，我差点就这么记下来了。
回头看代码，发现是归一化时拿 gold 的英文 key（`severity_estimation`）
去比模型输出的中文名（"严重程度估计"），根本不是一个东西，当然全 ×。
把中文名统一拍成 key 再比，才对上 2/3。教训：评测代码也要自测，
不然模型没冤枉你，你自己把自己冤枉了。

**5. zhipuai 在 python 3.14 上少依赖。**
装完 requirements 直接 import 报 `ModuleNotFoundError: No module named 'sniffio'`，
pip 没自动把 zhipuai 的这个传递依赖拉全。手动补了 sniffio，
也写进 requirements.txt 了。

## 和原论文差在哪

- 综述没有下游实验，我做的"让模型按框架判定文本"是我自己加的用法，
  论文没做这个，所以没有它的数字可以对照
- 测试集是我手写的 12 条中文文本，规模极小，不能当定量结论看
- gold 答案是我按 taxonomy 手工标的，带主观性，尤其模型类型参考值
- 模型只有 glm-4-flash 一个，没有换别的模型对比
- MLLM 这条线没测，因为测试文本全是纯文字，没有配图，
  没法验证多模态那部分

## 和我的研究方向的关系

我的方向是知识增强的多 Agent 灾害态势推理。这篇是"入门地图"，
这次复现相当于把地图上离我最近的那一格——响应阶段、态势评估——
真的走了一遍：

- 综述把 Disaster Situation Assessment 单列成一个任务，证明这条路
  有文献支撑、不是我硬想出来的，这次工具落地的就是这一格
- 判定"是哪种灾害、多严重、怎么描述"这三件事，正好对应态势评估的三个
  细分，也就是我以后要做知识增强的落点
- R2 那个判错的案例说明：光靠模型自由判定，task 边界会糊。
  这恰好是"知识增强"能插一脚的地方——用领域知识给模型划清
  识别和评估的界线，用规则兜住模型类型的选择
- 再往后就是"多 Agent"：识别、评估、协调、救援这些子任务各派一个 Agent，
  按这套 taxonomy 分工，框架本身就是一张现成的分工表
