# Sim911 复现笔记（第 63 篇）

> 复现论文：Sim911: Towards Effective and Equitable 9-1-1 Dispatcher Training with
> an LLM-Enabled Simulation（Vanderbilt + 纳什维尔应急通信部，AAAI 2025，arXiv:2412.16844）
> 用到的模型：智谱 glm-4-flash（API 调用）
> 时间：2026年10月

## 这项目干了啥

论文干的是给 911 调度员造一个"练功房"：拿真实呼叫记录攒出事实库和来电者画像，
让大模型扮演来电者陪新人接线员练手，还专门生成弱势群体（非母语、低收入社区、
无家可归、心理疾病）的呼叫场景来补公平性。

我照着做的是一条缩小的管线，核心就三块：**离线知识构建 → 受控生成 → 验证闭环**。
论文用美国 911 的真实记录 + GPT-4o，这两样我都没有，所以做了两个替换：

- 场景换成中文 120 急救。论文是"心跳骤停、独居老人、高层被困"这类，
  我这边换成"心脏骤停、独居老人、燃气泄漏、电梯困人"，情绪和句式都按国内接警的口吻写。
- 知识库自己手搓。论文的 11841 通真实呼叫我拿不到，就自己编了一份小的，
  放在 data/ 里，全是虚构的江城地址，但内部自洽，谁都能拿去复现。

规模说清楚：主评测 20 组「事件 × 画像」，公平性 8 组（同一个事件换 8 个画像），
两个消融各 20 组，加起来 68 组，每条都要生成 + 三项校验 + 最多 3 轮打回重生成。

## 三块分别是什么

**离线知识构建**（data/ 里四个文件）

- events.json：30 条事件规格，每条三样：事件类型、典型情境、特殊请求。
  比如 E01 是"心脏骤停 / 独居老人在家突然倒地、没有呼吸 / 家属不在场，只有邻居隔着门喊话"。
- profiles.json：8 个来电者画像，其中 5 个是弱势群体（非母语者、低收入社区居民、
  独居老人、情绪崩溃者、心理疾病来访者），另外补了听障代拨、儿童代拨、普通路人做对照。
  每个画像带一段"说话风格样例"，生成时当作 few-shot 注入。
- protocols.json：17 类处置协议，按事件类型分步骤。心跳骤停那类就是
  "确认意识 → 确认呼吸 → 呼叫 120 并取 AED → 开始按压 → 用 AED 除颤"。
- addresses.json：32 条虚构地址，江城路、和平里、幸福小区这些，门牌和小区名保持一致。

**受控生成**（generate.py）

给定一条事件规格和一个画像，让模型扮演呼救者开口。三样东西塞进提示词：
该事件类型的处置协议当背景、画像的说话风格样例当口吻、整张地址表当约束。
要求它按【地点】【呼救者原话】【求助要点】三个字段输出，地点必须从地址表里原样抄。

**验证闭环**（verify.py + run_eval.py）

生成完先查再收，三项：

1. 格式：三个字段齐不齐
2. 事实：地点在不在地址表里，而且这条地址有没有被呼救者真的说出口（这是论文
   "地址真实性"的直接对应）
3. 画像一致：把呼救者原话单独拎给模型盲猜是 8 个画像里的哪一个，猜中才算一致
   （对应论文的"画像识别率"）

不合规就把失败原因拼成一段话说给模型听，打回重生成，最多 3 轮。

## 怎么跑

```
# 装依赖
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

# .env 里填智谱 API Key

# 跑主评测 + 公平性 + 两个消融，结果写进 results/，有缓存可续跑
.venv\Scripts\python.exe run_eval.py

# 丢缓存全部重跑
.venv\Scripts\python.exe run_eval.py --fresh
```

## 踩过的几个坑

**模型直接把画像样例抄进正文。**
我一开始给的风格样例写得太像一段完整呼叫（独居老人那条是"喂……喂？是我，
我一个人住……我在家洗澡摔了一跤"），模型图省事，开头一字不差照搬。后来把样例
全改短，改成只体现口吻的片段，并在提示词里加一句"样例里出现过的完整短句一个都不许用"，
才基本压住。少数画像（比如 P2、P4）还是会零星抄，我认了，留在 results/samples.md 里。

**用"裁判猜中没"当硬门槛，闭环被裁判自己的噪声堵死了。**
最早画像一致也是硬门槛，结果第一版跑下来三条样本全部 3 轮用满还过不了。翻记录发现
裁判自己不稳：同一段"我……我住这儿，腿不行了"它有时猜 P3 有时猜 P2。裁判有噪声，
门槛就会一直打回，越打回生成的越差。后来改成分级：裁判猜中就算过，没猜中但把握度
低于 70 当"拿不准"也放行，只有"猜成别人且把握度 ≥70"才打回。改完一次通过率才从 0 恢复过来。

**画像风格和"必须说清地址"天然打架，注入画像反而拉低了地址真实率。**
这个是反直觉的。不注入画像时地址真实率 100%，注入以后掉到 85%。查记录才明白：
低收入社区画像的风格里就写着"习惯用『就那个卖早餐的旁边』这种相对位置描述地址"，
于是它真的只说"就那个卖包子旁边那栋"，地址表里选的那条没错，但原话里没说出口，
就被事实校验拦了（E27 连着三轮都是这个原因）。非母语者、心理疾病来访者也有类似问题，
情绪占满了，地址就漏了。我最后没去专门修它，因为这恰好是真实接警里的难处：弱势群体
报的警，位置信息就是更碎。代价是我的地址真实率到不了论文那种 99%。

**关掉地址表以后模型开始现编地址。**
消融的 no_kb 条件里，20 条首轮 20 条全是编的，60 次生成全部落空。编出来的有
"北京市朝阳区朝阳北路123号"、"上海市浦东新区东方路1234号"，还有干脆写成
"XX市XX区XX路XX号"占位符的。它甚至感觉得到自己没地址可用，就拿真实城市名现凑一个门牌。
这就是论文说的"没有事实库撑腰，模型会编地址、会悬浮"，一模一样。

**zhipuai 2.1.5 少了一个依赖。**
`import zhipuai` 直接报 `ModuleNotFoundError: No module named 'sniffio'`，
官方包没把 sniffio 写进依赖，得手动 pip install。已经在 requirements.txt 里补上了。

## 测试记录（真实数字）

完整条件（画像 + 知识库都开）20 组：

| 指标 | 首轮 | 最终 |
|---|---|---|
| 地址真实率 | 70.0% | 85.0% |
| 画像一致率 | 45.0% | 60.0% |
| 格式通过率 | 100% | 100% |
| 平均重试轮数 | 2.25（一次通过只有 25%） | |

两个消融摆一起看，论文那个结论是复现出来了：

| 条件 | 地址真实率 | 画像一致率(首轮) |
|---|---|---|
| 完整 | 85.0% | 45.0% |
| 关掉画像注入 | 100.0% | 15.0% |
| 关掉知识库（地址表+协议） | 0.0% | 40.0% |

关掉知识库，地址真实率 85% → 0%，60 次生成 60 次编地址。论文是 99.19% → 61.01%，
绝对值对不上（它用地理编码核，编的地址现实中存在也可能算过；我这张表只有 32 条，
模型编什么都命不中），但方向完全一致。

关掉画像注入，画像一致率 45% → 15%。裁判的判定分布也很说明问题：开着画像时它还
能猜出 P1/P2/P3/P4/P6 好几种，关掉以后 20 条里 12 条被猜成 P8（普通路人），
也就是"没特征、谁都不像"。论文那边是低收入社区画像识别率从 77.98% 腰斩到 44.44%。

公平性演示（同一个心脏骤停事件，换 8 个画像各来一遍）8 条的原文放在 results/samples.md。
放一起读风格差异肉眼可见：情绪崩溃者一直重复喊"他不动了！他不动了！"，
心理疾病来访者一半字花在"都是我的错"，非母语者在蹦单字，听障代拨在来回转述
"我问他一下啊"，普通路人冷静地把位置报清楚。5 个弱势画像里 3 个首轮就被裁判认出来了。

验证闭环到底拦下了什么，完整条件 20 组一共跑了 45 次生成，25 次是打回重来，失败原因：

- 地址没说出口 14 次（地址选对了但原话里没讲）
- 画像对不上 27 次
- 编地址 0 次、格式缺字段 0 次

格式这项从头到尾没派上用场，模型三个字段一次没漏。真正干活的是
"地址说没说出口"和"画像对不对得上"这两项。

## 和原论文差在哪

- 模型：论文 GPT-4o，我 glm-4-flash，档次差一截
- 数据：论文 11841 通真实 911 呼叫，我手搓 30 条事件规格 + 8 个画像
- 校验手段：论文用 BERT 算对齐、RoBERTa-QA 验地址、Google Maps 地理编码，
  我全用一段 prompt 让 glm 自己当裁判
- PPL 指标：论文能算（有真实呼叫当参照），我没法算，换成了地址真实率和画像一致率
- 用户研究：论文请了 10 名应急人员打分，我没条件做
- 语言：论文是英文 911，我是中文 120，句式、口吻、地址格式都是照国内改的
- 敏感性处理：论文说"敏感标签在运行时对模型隐藏"，我这边没做这个隐藏，简化掉了

## 和我的研究方向的关系

我方向是知识增强的多 Agent 灾害态势推理与辅助决策，这篇补的是**"陪练仿真器"**这一环。
它跟前面几篇的位置不太一样：ReAct、AutoGen 那几篇是在造能推理能协作的 Agent，
Sim911 是把这套技术反过来用来"训练人"。但底层是同一件事：知识库怎么建、
检索到的东西怎么受控地注进生成、生成完怎么用闭环把它压回事实。

论文替我验证了一个我课题里的关键假设：**知识库 + 检索增强 + 验证闭环**的范式
在应急一线是真好使，关掉知识库指标立刻雪崩。另外它提醒了我一个原来没系统想的维度：
如果辅助决策系统只在"正常场景"数据上搭，弱势群体就会被结构性忽略。我这次专门
把 5 类弱势画像单独拉出来做公平性对比，就是为了把这件事写进我的设计目标里。

再往前一步，它这个"来电者画像"再往前走一点就正好是多 Agent：接线员、调度员、
现场指挥各自扮演、互相传递态势。现在的仿真里只有一个来电者 Agent，后面可以扩成
一问一答甚至多方通话。论文做的是"练"（陪练），我做的是"判"（辅助决策），
一个练一个判，底层技术同源。
