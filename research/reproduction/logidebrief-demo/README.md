# LogiDebrief 复现笔记

> 复现论文：LogiDebrief: A Signal-Temporal Logic based Automated Debriefing Approach
> with Large Language Models Integration（Vanderbilt + 纳什维尔应急通信部，IJCAI 2025，arXiv:2505.03985）
> 使用模型：智谱 glm-4-flash（API 方式，不依赖本地显卡）
> 复现时间：2026年10月

## 这个项目做了什么

我给"120 急救接警通话"做了一套自动事后复盘，核心不是让大模型通篇读完再拍脑袋下结论，
而是照论文的骨架搭三层：先把规程写成带时间窗的硬约束（谁在多少秒内必须做某件事），
再让 GLM 当公式里一个个"判断零件"（这通电话算哪类、某句话算不算做了某个动作），
最后聚合成一张 Yes/No/Refused/NA 的质检单，每条结论都能点回去看是第几轮、原话是啥。

论文是在纳什维尔 911 上做的，2215 条需求、57 类通话、6 类致命情形。我做小做真，
自己写了一份中文精简规程（20 条需求、6 类通话、6 类致命情形），造了 12 通模拟通话，
真调 API 跑完，拿我自己标好的答案去核对。跑出来的数字和踩的坑都写在下面，没有一句是编的。

## 怎么运行

```bash
# 装依赖（第一次）
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

# .env 里填智谱 API Key（格式：ZHIPUAI_API_KEY=你的key）

# 全跑 12 通，结果写进 results/
.venv\Scripts\python.exe debrief.py

# 只跑前两通（调代码时用）
.venv\Scripts\python.exe debrief.py --limit 2

# 忽略缓存、重新调一遍 API
.venv\Scripts\python.exe debrief.py --no-cache
```

第一次跑完会把 GLM 的原始回复缓存到 `results/llm_raw.json`，再跑就直接读缓存，
不重复烧 token。改了通话内容记得加 `--no-cache` 或者把缓存删了。

## 这个骨架是怎么拼起来的

论文那句"各干各擅长的"我照着拆成三块。

第一块是规程库。一条需求长这样：`R11 无呼吸时指导胸外按压`，适用 CARDIAC 类通话，
触发条件是"判定患者没呼吸"，要求的动作是"指导胸外按压"，时间窗是"判定没呼吸之后 60 秒内"，
致命情形标签是 CPR。翻译成 STL 就是 `G( (CARDIAC ∧ 判定没呼吸) -> F_[0,60] 指导胸外按压 )`，
说人话就是"只要确认没呼吸了，那 60 秒内必须出现胸外按压指导"。20 条需求里，
8 条是通用项（地址、回拨电话、派车、现场安全、年龄、发病时间、安抚、结束前复述地址），
剩下 12 条按通话类型分给心脏、外伤、噎食、产科、火灾五类场景。

第二块是时间窗判断，放在 `stl.py`。真 STL 要装 RTAMT 那种求解器，太重了，我直接用
规则加时间比较顶替：每个需求算出一个 `[lo, hi]` 窗口，锚点可以是通话开始、通话结束，
或者某个动作（比如"判定没呼吸"）第一次出现的那一刻；然后看要求动作出现的时间落没落在窗口里。
这块就是论文里 DETECT/SCAN 的机械部分，`eval_requirement()` 返回 Yes/No/Refused/NA 加一句理由。

第三块是 LLM 判零件，在 `detector.py`。分两个函数：`classify_call()` 判通话类型、
事件类型、致命情形、响应力量，对应论文的 SCENE/TYPE/CRITICAL；`detect_actions()` 一次性把这通
电话里 24 个动作挨个判成 present/absent/refused，并给出证据轮次和原话，对应 DETECT/SCAN。
两个都强制返回 JSON，解析时做了兜底（去 ```json 围栏、抠第一个 `{}`、失败重试三次），
免得模型多写两句话整通就崩了。

## 跑出来的真实数字

（glm-4-flash，12 通，20 条需求，一共 240 个"通话×需求"判定）

| 指标 | 数值 |
|---|---|
| 判定一致率（Yes/No/Refused/NA 四类全算） | 96.7%（232/240） |
| 通话类型判定准确率 | 100%（12/12） |
| NA 判定（不适用项筛除）一致 | 114/114 |
| 违规检出 命中/误报/漏报 | 5 / 5 / 2 |
| 违规检出 精确率 / 召回率 / F1 | 50.0% / 71.4% / 58.8% |
| Refused 判定命中 | 0/1 |

我故意埋了 7 条违规（漏问发病时间、没指导止血、没指导解阻、没给分娩指导、
没做危险源警告、溺水那通没做 CPR 也没提 AED），模型逮住 5 条、漏掉 2 条，
另外多报了 5 条其实没违规的。详细逐通结果看 `results/results.md`，每通一份质检单看 `results/C0X.md`。

几个典型：

- 溺水那通（C12）我故意让接线员去"侧过来拍水控水"，没做胸外按压。模型把"侧过来拍水"
  判成了胸外按压，于是 R11 给了 Yes——一条要命的真违规被漏报了。
- 噎食那通（C06）更逗，接线员只说了句"你让他坐直了别乱动"，模型把这个"坐直"判成了
  海姆立克手法，R16 又给了 Yes，也是漏报。
- 反过来，C06 的"告知已派车"里，接线员在 23 秒就说了"车派了"，104 秒又说了一次"我们已经派车了"，
  模型只取了后面那次，判超时违规，多报一条。C06/C08 结尾明明复述了地址，模型没认出来，
  又各多报一条。C10、C12 里"问现场安全"的话它也没认出来。
- 唯一一条拒绝样本（C11，家属直接说"你别问了我不知道"），我期望判 Refused，
  模型给了 present，没识别出拒绝。

## 踩过的坑

最大的一个坑是我自己的标注。第一版跑完，C02、C03、C12 冒出来几条"违规"，
我差点以为是模型坏了。逐条点开质检单一看，是我把时间戳写飘了：说好的"90 秒内问意识"，
我写成了第 92 秒；说好的"180 秒内安抚"，我写成了 182 秒；出入就两三秒。
更离谱的是 C10，我给那通标了"该问年龄、该问发病时间"，结果翻回去看通话记录，
我压根没写这两句台词。这几条全是模型判对了、我标错了。

这事挺有意思——质检单本来是查接线员的，结果先查出了我这个"出题人"的错。
我把数据改对了（把飘掉的时间戳拨回窗口内、给 C10 补上那两句），重跑，
一致率从 93.8% 升到 96.7%。所以这 96.7% 不是模型突然变好，是我把卷子改对了。

第二个坑是 zhipuai 在 Python 3.14 上直接 import 就报 `No module named 'sniffio'`，
它没把 httpx 那个依赖自动带上，得手动 `pip install sniffio`，我已经写进 requirements.txt。

第三个坑是"动作发生在几秒"到底听谁的。模型判 present 的时候只给一个证据轮次，
我拿那一轮的时间当动作发生时刻。问题是同一个动作可能在通话里出现好几次，
模型要是报了偏后那一次，窗口就判超时了——C06 的派车就是这么被冤枉的。
论文的 SCAN 是整条信号上找首次出现，我这里只取了一个点，这块我确实简化了，
够用但不严谨。

第四个是想当然的地方：我把通话类型当单一标签，C10 是火灾里有人被烟呛到没呼吸，
类型判成 FIRE，于是 CPR/AED 那几条需求全被筛成 NA，等于漏了心脏处置这一层。
现实里一通电话可能同时套多个协议，论文也是多协议叠加的，我这块简化了。

## 和原论文比还有哪些没做

- 论文在和领域专家一起拆了 2215 条需求、57 类通话，我手写了 20 条、6 类，规模差两个量级
- 论文用 CitySpec、nl2spec 把手册离线翻成 STL 公式，我是手写窗口参数，没做自动翻译
- 论文造了 13200 通仿真 + 1244 通真实通话，我只有 12 通手搓的
- 论文单检查 F1 94-95%（GPT-4o），我这套小模型 + 小样本 F1 只有 58.8%，
  而且口径完全不一样（它测的是 2215 条需求级别的复核，我只有 20 条），两个数不能相减
- 论文的部署效果（省 311.85 小时、覆盖率 73.96%→85.05%、单通不到 30 秒）我没有环境复现
- 论文的 27 人用户研究我也做不了

## 和我的研究方向的关系

我方向是知识增强的多 Agent 灾害态势推理与辅助决策，这篇给我补的是"灾后复盘闭环"这一环——
系统光会给建议不够，建议合不合规程、有没有漏步骤，事后得能机器查。

更让我在意的是它验证了论文里那个疑问：形式化的外壳（STL）能保证"结构正确"，
每条结论都挂得住需求和时间窗；但壳子里那些 LLM 零件判错了它挡不住。这次 C12 把"拍水"
认成按压、C06 把"坐直"认成海姆立克，就是活例子——结构上 R11、R16 都"按时出现了"，
结论却是错的。这正好说明：可追溯的质检单不是终点，零件本身的可靠性才是那条及格线。
往我的方向靠，这套"形式化外壳 + 语义零件 + 可追溯结论"的写法，可以直接搬去给
灾害辅助决策做审计，让我后面那些多 Agent 的输出变得可查、可追责。
