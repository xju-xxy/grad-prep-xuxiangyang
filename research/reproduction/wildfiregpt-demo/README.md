# WildfireGPT 复现笔记

> 复现论文：WildfireGPT: Tailored Large Language Model for Wildfire Analysis（宾大 + 阿贡国家实验室，arXiv:2402.07877）
> 使用模型：智谱 glm-4-flash（对话）+ embedding-3（检索），API 方式，不依赖本地显卡
> 复现时间：2026年10月

## 这个项目做了什么

把论文里那个"给野火分析用的 LLM Agent"用中文本地化地搭了一遍。论文的整个系统其实是一个
LLM Agent 套一层 RAG，交互分三个阶段：

- 先问诊，把用户的身份、担心什么、关注哪里、什么时候要结果问清楚，汇总成一份用户画像
- 再根据画像生成一份行动计划，拿给用户确认
- 最后按计划去知识库里检索资料，生成带引用的分析建议

我做的是命令行版的这套流程，把论文里的野火场景换成了中文的"林场春季计划烧"咨询。
论文用 all-MiniLM-L6-v2 加 Faiss 做文献检索，我这里换成了智谱的 embedding 接口，
后面会讲为什么这么改。

## 怎么运行

```bash
# 第一次使用：建虚拟环境、装依赖
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

# 在 .env 里填智谱 API Key（格式：ZHIPUAI_API_KEY=你的key）

# 交互模式：自己跟它聊
.venv\Scripts\python.exe agent.py

# 非交互模式：跑固定的计划烧案例，把全过程写进日志
.venv\Scripts\python.exe agent.py --auto --log results/auto_log.md

# 只测检索那一段
.venv\Scripts\python.exe kb.py "春季计划烧 窗口期 气象条件"
```

## 知识库是怎么整的

论文的文献库是它自己的 CIACC 工具接的真实论文，我这边拿不到，就自己攒了一份。
一共 50 条，每条是一个短知识片段，带 id、分类、标题、正文：

| 分类 | 条数 | 举例 |
|------|------|------|
| 火险指标 | 7 | FWI 是什么、FFMC/DMC/DC/BUI 各代表什么、FWI 等级怎么对应防控措施 |
| 植被与燃料 | 7 | 地表火/树冠火/地下火、针叶林为什么易燃、阔叶林为什么耐火 |
| 控制烧与计划烧 | 7 | 窗口期怎么选、气象门槛、生态作用、安全线准备、审批报备 |
| 应急物资与装备 | 6 | 风力灭火机、二号工具、个人防护、直升机灭火 |
| 气象与地形 | 5 | 风/坡度的作用、山谷烟囱效应、干雷电引火 |
| 防火隔离与工程 | 5 | 隔离带、生物防火林带、防火道路网、林火阻隔系统 |
| 社区防护与疏散 | 5 | 防御空间、房屋防火改造、疏散预警、WUI |
| 监测预警 | 3 | 卫星热点、瞭望塔、火险等级发布与禁火令 |
| 生态与恢复 | 3 | 火后恢复、火后次生灾害、迹地复燃 |
| 法规与管理 | 2 | 防火期用火审批、防火责任制 |

内容是我从公开的林火科学和森林防火科普资料里整理、再改写成中文条目的，
不是原文照抄，目的就是给检索一个能用的语料底子。

## 检索这一块，我做了裁剪

论文用的是 all-MiniLM-L6-v2 做 embedding，再加 Faiss 建向量库做 k 近邻搜索，
这套组合成本低速度快，很适合原型。我本来也想照着上 sentence-transformers，
但本地装它要拖下来一大坨依赖（torch 那一套）和模型权重文件，网速和磁盘都不太配合，
对我的小语料属于杀鸡用牛刀。所以我改了方案：

- 检索优先走**智谱的 embedding 接口**（`embedding-3`，实测每条返回 2048 维向量），
  把 50 条知识一次性算好存本地缓存（`data/kb_vectors.json`），query 时算余弦相似度取 top-k。
  这相当于把 Faiss 的 kNN 用 numpy 手写了一遍，对 50 条的量级完全够用。
- 如果接口调不通，就自动退化成**关键词加字符重合度**的朴素检索（中文按两字片段切，算重合比例）。
  代码里 `kb.MODE` 会打印这次到底走了哪条路，跑的时候能看见。

我实际跑的是向量检索这条。要说差别：论文的向量是本地模型算的、离线、免费且能批量；
我用在线接口，每查一次要发一次请求，但省了本地环境。这算复现里最容易说清、也最合理的一处降级。

## 三个阶段在代码里怎么落地

**画像阶段**的关键是别让模型一口气抛一堆问题。system prompt 里写死了"一次只问一个，
最多问 5 个"，问够了就让它吐一个 `PROFILE_READY` 加一段 JSON 画像。
程序靠这个标记判断该继续问还是该收口。

**规划阶段**让它基于画像生成一份计划，包括要用哪几类知识、分几步分析、最后给什么建议，
然后等用户确认。交互模式可以直接回车同意，也可以提意见让它改。

**分析阶段**是 RAG 真正干活的地方。我先让模型自己把分析拆成 3 个步骤，
每个步骤配一句检索查询词；程序拿查询词去知识库检索，把命中的原文连同 id 一起塞回提示词；
模型再写带 `[条目id]` 引用的分析。检索永远由程序做，模型拿到的都是真实条目，不许它自己编。

系统提示词里我加了一条：如果不同知识条目之间有冲突，要指出来，不要硬拗成一致。
加上这条之后输出确实更老实一点。

## 踩过的坑

**最大的坑是自动问答答非所问。** 为了能留痕、能重复跑，我做了个 `--auto` 模式，
用一套预设答案替用户回答问诊问题。第一版我图省事，写成"第几个问题就回第几条答案"，
结果模型每次提问的顺序和措辞都不一样，第二轮它问的是时间线，程序却把地点那条答案塞了过去，
画像直接串味。我盯着日志才发现，不是模型在乱说，是我这边的假答案错位了。
后来改成按问题里的关键词路由（问题里带"经验/背景"就回身份，带"时间/多久"就回时间线），
同一个答案不重复使用，才对上。

**zhipuai 装完缺依赖。** 新的 zhipuai 包 import 的时候会缺一个叫 sniffio 的间接依赖，
直接报 `No module named 'sniffio'`。这个坑上一篇 AutoGen 复现我也踩过，这回在
requirements.txt 里把它补上了。

**模型会把"收集资料"当成分析步骤。** 第一版让模型拆分析步骤，它拆出来的第 1 步是
"收集火险指标、气象数据、地形图"，这根本不是分析，是准备工作，检索也无从下手。
在提示词里点明"步骤要针对具体问题，不要写收集资料这类空步骤"之后好多了。

## 测试记录

用固定的计划烧案例跑通了完整三阶段，真实输出在 `results/auto_log.md`，
我挑出来讲的重点放在 `results/results.md`。几个能对得上的地方：

- 问诊问了 5 个问题，最后汇总的画像 JSON 里 role / concern / location / timeline / focus 都有值，
  且和用户答的内容一致，没有编造。
- 分析阶段三步的检索都有程序打印的"命中哪几条"，比如第 2 步查询
  "春季华北地区气象条件对计划烧的影响"，命中 `BURN-02`、`BURN-06`、`BURN-03`、`BURN-07`，
  四条都是控制烧直接相关的，这一步检索质量最好。
- 生成的每段分析都能一一对应到命中条目的原文，没有出现知识库里查不到的数字或说法。

没搞定的地方也记一下：这个案例用户明明问的是"平衡生态和居民区风险"两头，
但画像阶段 focus 只记下了安全和防护，把"维护橡树更新"这个生态目标弄丢了，
结果后面三步一路只谈防火，知识库里那条 `BURN-04 计划烧的生态作用` 全程没人引用。
最后给的建议是一份合格的安全指南，但不是用户要的"怎么平衡"。
这块没完全搞定，也让我觉得瓶颈不在检索、不在模型，而在画像有没有建全。

## 和原论文比还有哪些没做

- 论文的数据源是 ClimRR 的 FWI、WFIGS 的近期野火记录、NAFSS 的历史火疤数据，
  我这些都没有，只有自己攒的知识库，所以论文里"位置数据 + 文献"双通道检索，
  我只做了文献这一半。
- 论文的文献检索是 all-MiniLM-L6-v2 + Faiss，我换成了在线 embedding 加手写余弦，理由上面说了。
- 论文做了 4 个案例，还找了领域专家按正确性、相关性、蕴含性、可及性四个维度打分
  （97.73% / 98.20% / 93.75% / 95.49%）。我只跑了 1 个案例，没有专家评分，只能自己看输出合不合理。
- 论文支持多轮对话、用户中途说"再深入讲讲某一步"，我这边三阶段走完就结束了，没有接着深挖的环节。

## 和我的研究方向的关系

我方向是知识增强的多 Agent 灾害态势推理与辅助决策，这篇是我目前读到的、
把 Agent 加 RAG 在灾害领域落地得最完整的一个。对我有两点直接的启发：

一是"问诊 → 规划 → 分析"这个三段式。它把模糊的用户问题一步步收敛到能动手的问题上，
比上来就瞎答体验好很多；而且规划那步要用户点头，等于给灾害决策留了个人工把关的口子，
这个设计我以后做辅助决策系统会照搬。

二是这次跑出来的教训：画像少写一条，后面全歪。多 Agent 系统里如果有个 Agent 专门负责
理解需求，它的输出质量就决定了整条链的上限——这可能比"再加一个检索 Agent"更值得花力气。

   试试能不能救回这次漏掉的生态目标
2. 检索上试试多查询合并（一个步骤生成两三个查询词，结果去重），看能不能减少跑题条目
3. 把这篇和上一篇 AutoGen 合起来：现在三个阶段是一个 Agent 干所有活，
