# CrisisBench 三层打分细则（Rubric）

> 版本：v0.3（可核验结论版）· 配套数据：[scenarios.json](scenarios.json)
> 本文件是论文"评测协议"章节的素材，评审和复现者都按这份规则打分。

## 一、总原则

1. **checklist 式判定**：每个要点独立判 0/1，不做程度评分（0.5 分不存在），保证可复现。
2. **采点不算错点**：只检查"该说的说了没有"，不惩罚无关内容（除非决策层出现**资源超配**，见§四）。
3. **同义算命中**：判定时允许同义替换（"撤离"="疏散"），以要点文本语义为准，不以字面为准。
4. **两句来源**：规则打分（关键词匹配）用于快速自检；**正式评测一律以 LLM 打分 + 人工抽检为准**（§六）。

### v0.2 → v0.3 的两次校准（写进论文的"基准构建过程"）

- **v0.2 教训一：事实层满分无区分度。** 情报直接送达，事实要点几乎都能抄到。→ v0.3 为每个场景新增 1-2 条**数值推算型要点**：关键数字不直接出现在情报里，必须跨 2-3 条情报推算（如 240 户×每户留守 1-2 人≈300-500 人；6 公里÷时速 1-1.5 公里≈4-6 小时）。
- **v0.2 教训二：裁判方差过大。** 同一批回答，glm-4-flash 原提示词几乎全判 1，glm-4-plus 加"宁严勿松"提示词后推理/决策层几乎全判 0。→ v0.3 双管齐下：① 要点全部改写成**可客观核验的具体结论/具体措施**（不再考"链条写没写全"这种模糊项）；② 裁判提示词取中间口径（§六.2），并保留双模型交叉裁判（§六.3）。
- 两次校准的数据都保存在 [results](../results/) 目录（v0.2 原始裁判与 plus 重裁判文件），作为裁判可靠性分析的证据。

## 二、事实层（Fact）

- **考什么**：智能体回答里有没有"捡全"该场景的关键情报要素。
- **怎么判**：逐条对照 rubric 里的"事实层"要点，回答提到即 1 分，未提到 0 分。
- **数值推算型要点（v0.3 新增，要点文本注明"推算"）**：回答必须给出**推算出的数值或数值区间**才算满足；只复述情报里已有的原始数字不算（如照抄"两村共约240户"不算推出"约300-500人"）。裁判对照情报原文核验数值是否推算正确。
- **得分公式**：事实层得分 = 命中要点数 ÷ 总要点数。
- **注意**：信息矛盾场景（如 S005）中"识别到矛盾本身"也是一条要点——只说其中一个数字、没意识到两个数字打架，不得分。

## 三、推理层（Reasoning）

- **考什么**：因果结论推没推出、敲没敲定。
- **判定标准（v0.3）**：每条推理要点的**判定对象是"结论"**——回答中明确表达出该条目的结论（措辞可不同，意思到位即可）且不与情报矛盾，得 1；结论未出现、出现相反结论，得 0。
  - 场景 JSON 中每条仍保留 `起点/机制/终点` 三字段，仅供人工核对与论文展示因果结构用，**不作为 LLM 裁判逐字对号的要求**（v0.2 的经验：要求逐字对号会让裁判方差爆炸）。
- **信息矛盾场景附加规则**：对矛盾的处理方式要"合理且说明依据"（采信哪个口径+为什么+留核查），只说"数据不一致需要注意"但无处理策略，不得分。

## 四、决策层（Decision）

- **考什么**：行不行动得起来。
- **判定标准**每条建议：**明确给出该条措施（有具体对象+具体动作）**得 1；笼统表述（"加强力量""做好工作""及时处置"）得 0；出现下列任一硬伤**该条不得分并记录扣分原因**：
  1. **无对象**：说了"立即撤离"但没说撤谁、撤哪（场景中对象必须落到具体村庄/人群）。
  2. **资源超配**：动用了场景资源清单里没有的资源（如 S001 无直升机却"派直升机巡查"；S005 该镇实际可用 2 艘冲锋舟却按 8 艘部署）。
  3. **与情报冲突**：建议与已确认事实矛盾（如道路已断还"通过县道撤离"且未提绕行）。
- **得分公式**：决策层得分 = 有效得分的要点数 ÷ 总要点数。
- 陷阱型要点（水冲稀释、按编制清单而非实际可用资源调度等）在场景 JSON 的决策层中以"必须识破错误做法"的方式表述，识破并给出正确做法才得分。

## 六、打分实现（两种方式）

1. **规则打分（关键词匹配）**：用场景 JSON 中每个要点的 `match` 词表在回答文本中查找，命中 ≥1 词即得分。优点是免费、零波动；缺点是"提到词≠答对"，可能虚高或漏判（对推算型要点只能列出可能的答案数值）。定位：**开发自检用，不写入论文正式数字**。
2. **LLM 打分（正式）**：把"场景情报原文 + 评分要点清单 + 智能体回答"交给裁判模型（judge，可与被测模型同 API 但要独立调用、角色隔离），要求按唯一编号逐条输出 0/1 和一句理由。要点里注明"推算"的，裁判必须核对推算数值。judge 提示词模板（中间口径）：

```
你是灾害应急决策评测的独立裁判。下面是场景的评分要点（每条有唯一编号）和一个研判员的回答。
请逐条判断要点是否在回答中被满足，只输出 JSON 数组：
[{"编号":"F1","得分":0或1,"理由":"一句话"}]
判定规则：
- 事实层（F）：回答中准确陈述该要素（关键数值与情报一致或推算正确）得1；未提及或被错误陈述得0；要点注明"推算"的，回答必须给出推算出的数值或数值区间，只复述原始情报里的数字不算满足；
- 推理层（R）：回答中明确表达出该条目的结论（表述可以不同，意思到位即可）且与情报一致得1；结论未出现或与情报矛盾得0；起点/机制/终点仅作参考，不要求逐字对应；
- 决策层（D）：回答中明确给出该条措施、写明具体对象与动作得1；仅笼统表述得0；若目标对象完全缺失、动用了资源清单之外的资源、或与情报事实冲突，得0；
- 每条要点都必须给出判定，不得漏条；只判断要点是否被满足，不评判回答的其他内容；
- 你对所有回答按统一标准打分，不因措辞风格而放宽或收紧。
```

   - 解析端：按唯一编号（F/R/D+序号）映射回层与序号；裁判漏判按 0 分计并标注；解析失败重试 1 次。

3. **一致性与裁判可靠性**（论文"评测协议"章节的实证支撑）：
   - **双裁判交叉**：全部答案由 glm-4-flash 与 glm-4-plus 各打一遍分（`--judge-model` 参数指定裁判；`--rescore` 对同一批答案只换裁判重打分，保证"分数差=裁判差、与答案无关"）；报告两裁判逐条一致率与 Cohen's kappa。
   - **人工抽检**：随机抽 20% 场景，由标注者（我）复核全部 0/1 判定中的分歧项并裁定。
   - v0.2 校准期实测：flash（宽松提示词）≈全 1，plus（严格提示词）≈推理/决策全 0 —— 说明要点表述与提示词口径必须配合校准，v0.3 就是校准结果。

## 七、指标定义（会画进论文的图）

- **三层得分**：事实层/推理层/决策层各自的"命中率"（§二~四公式）。
- **综合得分**：三层等权平均，仅作总览排序用，论文正文以分层结果为主。
- **裁判一致率**：flash vs plus 逐条一致率 + kappa（§六.3）。
- **决策代价附加项**：记录每条推演的 API 调用次数与耗时，作为"协作成本"的对比维度。
